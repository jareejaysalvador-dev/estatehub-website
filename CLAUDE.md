## What EstateHub.ph is

A premium, trust-first Philippine real estate website. Positioning line from the founder's homepage mockup: *"Building generational wealth, one move at a time."* Services: Lease, Property Management, Sales, Business Solutions. Tone: established and secure (bank-like), not playful (startup-like).

**Legal structure: EstateHub.ph is a One Person Corporation (OPC)** under the Revised Corporation Code (RA 11232) — a single-stockholder corporation registered with the SEC, not a DTI sole proprietorship. Load-bearing consequences: it has separate legal personality (can own IP, license software, invoice internationally, hold contracts in the company name), it carries a limited-liability shield that matters for the cross-border compliance exposure any messaging/AI product creates, and it converts to an ordinary stock corporation by statute if a second shareholder is ever admitted — so the eventual SaaS-licensing ambition is not structurally foreclosed. Two things to confirm with counsel rather than assume: how RESA (RA 9646) licensed-broker-officer requirements interact with the OPC's officer structure, and whether NPC registration plus a Data Protection Officer are required as inquiry data volume grows. Do not describe the company as a sole proprietorship or as "a solo agent" anywhere in copy or planning.

**Confirmed business model: full-service brokerage**, matching Hoppler (commission-based, in-house licensed brokers handle the whole transaction), not a self-serve listings portal (Lamudi, OnePropertee, Dot Property, RentPad, Real.ph). This is settled, not an open question — it decides what "primary CTA" and "features" mean:
- "Contact us" / talking to an agent is the concierge/conversion path, not a secondary alternative to it — don't add a redundant separate "concierge" CTA (e.g. RentPad's "Help me find a place") on top of it.
- No self-serve-portal language ("free listing," "post your property") anywhere — sellers reach EstateHub the same way buyers do, through an agent.
- Search is the self-serve *complement* to "Contact us," not a competing primary action.
- Feature priorities follow Hoppler's playbook over a portal's: rent-vs-buy calculator, neighborhood guides, saved-listings, Messenger widget — not developer directories, classifieds, or lead-package pricing tiers.

**Confirmed: OFW/overseas buyers are a named audience, built in from the start** — not a later add-on. Dot Property is the only competitor serving this audience, and it's otherwise cluttered/ad-heavy, so a clean version is a real differentiator for a brokerage already selling "one point of contact." This needs actual supporting content, not a passing mention: a remote-transaction process explainer, Power of Attorney (POA) guidance (the standard real concern for a buyer who can't be physically present), and timezone-aware contact options. Likely surfaces as its own nav/section, or folded into how Sales and Property Management each explain themselves for a remote owner — decide the exact IA when building, but the audience and content commitments above are settled.

**Confirmed: introduce a serif for on-page headlines.** Matches Hoppler's specific premium/brokerage-not-portal signal (the one thing that most visibly separates it from every listings portal in the audit). Scope: this is for **headline/editorial copy only** (H1s like the hero headline, section headings) — the finalized wordmark/logo (`ESTATEHUB.PH` in Montserrat) does not change; Inter stays as the body/UI font.

Specific choice: **EB Garamond**, not Cormorant Garamond. Reasoning: Cormorant Garamond is already the serif in use on the unrelated Aya Hills project in this same workspace, and reusing it here would just be a repeated default rather than a considered pick. Playfair Display (the other obvious free option) is a high-contrast, fashion-editorial serif that reads more "luxury magazine" than "established, bank-like trust" — EB Garamond is a classical old-style Garamond revival, the same family long used in legal/financial/publishing contexts specifically for its credible, unshowy feel, which fits EstateHub's brief better than Playfair's drama. Revisit if you disagree, but don't default back to Cormorant Garamond or Playfair without a reason.

## Competitive research and design audit — full analysis

A complete synthesis of both source documents (layout, navigation, CTA placement, colors, typography, features, strengths, weaknesses, per-site and cross-site, plus EstateHub-specific recommendations) was written up in full during the planning conversation that preceded this restart. Regenerate or ask for that analysis if it isn't already visible in the current conversation — don't re-derive it from scratch if it was already produced. Headline points that should survive into any rebuild:

- **Persistent, nav-embedded search** (RentPad's pattern) is called "arguably the single best interaction-design pattern found across all eight audits" — the first build only had search in the hero, not the nav. Fix this next time.
- Homes & Land's homepage has **no search above the fold at all** — called the single biggest UX gap in the whole audit. Don't repeat it (the first build didn't).
- **One disciplined accent color** beats multi-color pages (Lamudi, Hoppler, RentPad, Real.ph vs. Dot Property's 5+ colors and Homes & Land's competing blues).
- **Cap primary nav at 5–6 items**; push secondary actions into dropdowns/account menus (Dot Property's 9-item nav and OnePropertee's 6-item secondary cluster are the cautionary examples).
- **Authentic local photography** (Hoppler's real Filipino family, OnePropertee's lifestyle shots) reads as more trustworthy than generic stock (Lamudi/MyProperty/Dot Property).
- Messenger/WhatsApp-style chat, not a generic chat bubble, matches local user habits.
- The audit's screenshots are **desktop-only** (~1280px) — mobile/responsive was explicitly not covered, despite PH traffic skewing heavily mobile. Don't assume desktop-audited patterns transfer to mobile without checking.
- Dot Property specifically serves **OFW/overseas buyers** with dedicated cross-border tools — confirmed as a built-in-from-the-start audience for EstateHub, see above.
- Competitors named in the research but not deeply audited: Trovit PH, FazWaz.ph, Presello, DMCIHomes.com, HousingInteractive.com.ph.

Full write-up: `estatehub_handoff/analysis/research-synthesis.md` (also published as an Artifact during planning).

## User journeys (planned)

## Accessibility spec — implemented

`estatehub_handoff/analysis/accessibility-spec.md` makes the locked WCAG 2.1 AA baseline concrete across keyboard navigation, contrast, alt text, form labels, focus indicators, and font sizes. **The two design-system amendments it produced are implemented and empirically verified**: focus rings are Deep Emerald on light surfaces / Mint on dark via a `--ring` custom property flipped by `.surface-dark`/`.surface-light`, confirmed in-browser to render as real `#178a57` 2px outlines on genuine keyboard focus (and correctly absent on non-keyboard focus); input borders use Slate. ## Content management (Sanity CMS) — implemented

Listings, brokers, and site settings (contact email/phone, Messenger page ID) live in a Sanity dataset instead of hardcoded files, editable via a Studio deployed **off-domain** at `estatehub.sanity.studio` (project ID `0wtk03lk`, dataset `production`) — this preserves the site's zero-admin-surface architecture below: there is still no login/database/admin route on estatehub.ph itself, just a public read-only client (`src/sanity/client.ts`, no auth token — the dataset is intentionally public-read) querying a separate, off-domain product.

**Studio source lives in `studio/`**, a self-contained Sanity project (own `package.json`/`node_modules`/`tsconfig.json`; its own `.gitignore` correctly excludes `node_modules`/`dist`/`.sanity`) committed to this same repo. **Critical, and worth restating because it already caused a real outage: `studio/` must stay excluded from the root `tsconfig.json`'s `exclude` array.** The root tsconfig's `include` is a `**/*.ts` wildcard that picks up `studio/**` by default; without the exclusion, `next build`'s TypeScript check tries to resolve `studio/sanity.cli.ts`'s `sanity/cli` import using the *root* `node_modules` (which doesn't have the `sanity` package) and fails — but only on a clean clone. A local build can pass anyway if `studio/node_modules` happens to still be on disk from a previous `sanity init`/`npm install`, which is a false negative: this exact scenario caused three consecutive failed production deployments (~36 minutes of stale production) before being caught by comparing against Vercel's actual deployment history. **Lesson that generalizes: after adding any new subdirectory with its own dependencies to this repo, verify the root build in a way that doesn't rely on locally-cached `node_modules`** (e.g., temporarily move the suspect `node_modules` aside and rebuild) rather than trusting a local pass at face value.

**Schema** (`studio/schemaTypes/`): `listing` (title, slug, status radio For Sale/For Lease, type dropdown, location, price, beds, baths, floorAreaSqm, lotAreaSqm, blurb, neighborhood, photos array with alt text, broker reference). Required: title, slug, status, type, location, price, photos (min 1), broker. **Deliberately optional, not oversights**: blurb and neighborhood (the detail page hides each "About..." section entirely when empty, same conditional pattern already used for beds/baths/area — not a heading over nothing), and per-photo alt text (explicitly recommended *against* relaxing — it's an accessibility requirement, not content-completeness, and generic auto-generated alt text wouldn't have solved the real problem either — but the user heard the tradeoff and chose to relax it anyway; `resolveImage()` already defaulted a missing alt to `""` before this, so no code changed beyond the schema).

**Real slug bug, found and fixed via a live listing, not hypothetically.** The first real published listing had `slug.current` = `"Single detached unit"` — spaces, a capital letter, typed by hand into the field instead of using the "Generate" button. Symptom was confusing: the page 404'd on click, but the browser tab title still showed the correct listing name (metadata resolution and the page body apparently don't fail identically here). Root cause: the `slug` field had no `slugify` function and no format validation, so free-typed text passed straight through ungated. Fixed two ways — `options.slugify` now forces lowercase-hyphenated output when "Generate" is clicked, and `validation` rejects anything else outright with a message pointing at "Generate" instead of typing it manually (both live at `estatehub.sanity.studio`, deployed directly via `npx sanity deploy` from `studio/` — this doesn't go through the website's own Vercel pipeline at all). `PropertyCard.tsx` also now wraps the slug in `encodeURIComponent()` when building the link, as defense-in-depth, though the schema fix is what actually prevents recurrence.

**Query layer** (`src/sanity/`): `client.ts` (public client, `useCdn: true`), `image.ts` (resolves Sanity image refs to `{url, alt}` via `@sanity/image-url`'s named `createImageUrlBuilder` export — not the deprecated default export), `types.ts`, `queries.ts` (`getAllListings`, `getListing`, `getAllListingSlugs`, `getAllBrokers`, `getSiteSettings`, all GROQ, all async). **Findings below are the underlying market/AI research, independent of the GHL-specific decision — still don't re-derive them:**

- **The category is structurally inapplicable here, not merely expensive.** Every major platform's loop is MLS feed → IDX site → behavioral signal → nurture trigger, and there is no Philippine MLS. Sierra's own docs say its flagship AI "is not available for IDX-only accounts"; Follow Up Boss cannot call or text outside the US/Canada.
- **The evidence supports reliability, not intelligence.** 48% of buyer inquiries to brokers are never answered (WAV Group); NAR 2025 found 46% of agents report *no noticeable impact* from AI and that they use ChatGPT, not their CRM's AI. Instant, reliable response captures most of the available gain with no ML at all.
- **Extraction works from zero data; prediction does not.** LLM extraction of intent/budget/timeline from free text is buildable today. Predictive scoring needs 100–300 conversions and 6–24 months — defer it, and don't let anyone sell it as day-one.
- **Messenger has a hard 24-hour messaging window**; the 7-day Human Agent tag cannot be used by automation. Long-horizon Messenger nurture is not buildable — Messenger is for the live window, long-tail nurture runs on email only (this section originally said "email/SMS" — superseded by the SMS finding directly below).
- **SMS marketing to Philippine numbers is effectively closed, not merely expensive.** Mandatory sender-ID pre-registration since April 2025 (LOAs to both Globe and Smart), promotional content is disallowed outright on registered sender IDs, Twilio's own PH content rules name real estate specifically as spam, and URLs are banned (no listing links). OFW markets (UAE, Saudi Arabia) are more restrictive still. Budget SMS at zero; a narrow transactional-only exception (e.g. a viewing reminder, never marketing) could later use a cheap local gateway (Semaphore, PhilSMS, ~₱0.50/msg) — never GHL's Twilio path at ~25× the cost.
- **Disclosure paradox** (Luo et al., *Marketing Science* 2019, n=6,200+): undisclosed bots matched proficient humans, but disclosure cut purchase rates 79.7%. Design any conversational AI *assuming disclosure*, for a narrower job than vendors imply.
- **Meta Business Agent** (global June 2026, ~4–5¢/message, free for small businesses) is commoditizing AI lead qualification inside Messenger. Don't build a moat there.
- **The PH OFW niche is contested** — Homeward.ph (one broker, tools-first, country-segmented OFW guides) and Bahai Deals (Talino/RCBC, diaspora-focused) already occupy adjacent ground. **The verified gap is the remote-transaction mechanics** (POA/SPA sequencing, consularization, country-specific document checklists), absent even from Ohmyhome's OFW page.
- **The first MVP requirement was unglamorous, and is now partly done:** durable lead persistence (`/api/inquiry` → Supabase `leads` table) exists. Still missing: lead IDs/timestamps come free from Supabase (`id`, `created_at`), but **source attribution does not** — the inquiry form/API still captures no UTM parameters, referrer, or landing page at all. Also still unbuilt: every "Message us on Messenger" entry point site-wide (`MessengerWidget`, `StickyInquireBar`, `AgentBlock`, the contact page, `ContactFormFields`) links to the same bare `https://m.me/{pageId}` with no property context, despite `m.me` supporting a `?ref=` parameter built for exactly that. Both remain small, standalone website changes, unrelated to the GHL-vs-Supabase question.
- **`leads` table schema (Supabase) — pre-existing table, not created by this codebase's SQL.** Verified via `information_schema.columns`: `id` is **`bigint`** (Table Editor's default identity column, not the `uuid` originally specified — harmless, nothing in the code reads or constructs an `id`), `created_at` (`timestamptz`, not null, default `now()`). `first_name`, `last_name`, `phone`, `email`, `source`, `property_interest`, `notes`, `qualification_status` **all exist but are nullable at the DB level** — the `create table if not exists`/constraint statements given to the user no-op'd against this already-existing table; only the later `alter table add column if not exists` calls (`notes`, `qualification_status`) actually took effect. **Mitigated, not fixed:** `/api/inquiry` validates `firstName`/`lastName`/`phone`/`email` before ever calling Supabase, so a real form submission can't produce a blank row — this gap only matters for something else inserting into this table directly, which nothing currently does. Don't "fix" this by altering the live table without a real reason; the `id` type especially isn't worth touching. `source` is hardcoded `"Website Contact Form"` from `/api/inquiry`; `property_interest` holds the intent radiogroup value (buy/rent/sell/manage/business/overseas), not a listing reference; `notes` is just the message field now, no prefix; `qualification_status` is left null at submission, set manually later. **`regarding_property`** (added later, `alter table ... add column if not exists regarding_property text;`) holds the listing title from the `/contact` page's "Regarding: ..." banner when reached from a property detail page — this used to be folded into `notes` as a `Regarding: <title>\n\n` text prefix before the dedicated column existed; that duplication was removed once it had its own column. Real listings exist now, so this is no longer a no-op. RLS: public/anon can `insert` only, no `select` — the publishable key in `.env.local` cannot read leads back, by design, which also means nothing in this codebase can verify a row was written or deleted; that's a dashboard-only operation.
- **Confirmation email (Resend) — built, debugged, confirmed working in production.** `/api/inquiry` sends a personalized confirmation email via Resend's REST API directly (no SDK dependency; `src/resend/client.ts`) after a successful Supabase insert — best-effort, wrapped so a failed send is logged but doesn't fail the request, since the lead is already captured by that point. **Real gotcha hit and fixed:** `sendEmail()` returns `null` (not a throw) when `RESEND_API_KEY` isn't configured, so a missing key failed completely silently — 200 status, zero outgoing requests, no error anywhere — until an explicit check-and-log was added for exactly this case. That first real incident's root cause was Vercel's env-var-at-build-time behavior: adding a var to the dashboard doesn't reach an already-built deployment, needs a fresh one. Env var: `RESEND_API_KEY` (`.env.local` + Vercel).
- **One-way Supabase → Google Sheet sync exists, deliberately outside this repo.** Script + setup docs live at `C:\Users\jaree\Documents\estatehub-leads-sheet-sync` on the owner's machine (unrelated deliverables never go in this repo, per standing preference). **Load-bearing finding, worth keeping so it's never re-debugged:** Supabase blocks `service_role`-key requests it detects as browser-like, purely via User-Agent string pattern-matching — verified directly, a Chrome-style User-Agent alone triggers `"Forbidden use of secret API key in browser"` with zero other browser-like headers (no Origin/Referer needed) present. Google Apps Script's `UrlFetchApp` cannot override its own default User-Agent (confirmed by testing the fix and watching it fail identically, not assumed), so Apps Script can never call Supabase directly with a secret key. **Solution: `/api/leads-sync`** (this repo) proxies the request — holds the real `SUPABASE_SERVICE_ROLE_KEY` server-side, while Apps Script itself only ever holds `LEADS_SYNC_SECRET`, a separate narrow token scoped to this one endpoint, so the actual database credential never touches Apps Script's storage even indirectly. New env vars: `SUPABASE_SERVICE_ROLE_KEY`, `LEADS_SYNC_SECRET` (`.env.local` + Vercel).
